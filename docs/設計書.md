## 1. ゴールとこの設計の役割
- ゴール：2チャンネルで毎日1本ずつ（合わせて毎日2本）、10分前後の長尺を出す（型D の AI検証の回は20〜25分）。作る作業はほぼ人の手を使わない。広告収益と LINE 登録（その先のアフィ）を最大にする。人の作業は、API の審査が通るまで週約40〜80分、通った後は週平均約15〜30分（幅の理由は §10。段階Bで確定する）。
- 収益に一番効くのは速さ。当たる型を早く見つけ、本数と予算をそこに寄せる。この設計は、探す・判定する・寄せるを自動で回すことを最優先にしている。
- 収益は2本立て。広告は収益化の条件を越えてから、アフィは LINE 登録の初日から入る。だから LINE の登録後の流れ（§5A）も最初から作る。
- ショートを使わない理由は3つ。
  - ショートは説明欄のリンクが押せないので、LINE につながらない。
  - 1再生あたりの単価が長尺よりずっと低い。
  - 長尺とショートは視聴者が分かれやすい。
- 代わりに、型を探す速さは次の2つで補う。
  - 競合調査の実績で、候補の型を事前に絞った（チャンネルごとに今の型と、フルAIの競合で当たっている型D）。
  - 探索期は毎日出す。
- この設計で決めないこと：各チャンネルの題材と型。競合調査の結果をもとに `channels/<ch>/手順書.md` に書く。

## 2. 1日の流れと、数字の回し方

### 毎日（チャンネルごと）
```
[ネタ帳] → ①ネタ → ②調べもの（出典つき）＋自前データ → ③台本 → ④台本ゲート
  → ⑤声 → ⑥絵（前日にまとめて頼む） → ⑦絵ゲート
  → ⑧組み立て（音量そろえ込み） → ⑨完成品ゲート → ⑩サムネ2案・タイトル3案
  → ⑪アップ（在庫に入る／二重アップ防止） → ⑫記録
在庫から公開予約する（審査後は毎日自動。審査前は本人が週1回まとめて7本ずつ）
```
- 在庫の目標は、審査の前と後で変える。どこかの段で不合格や失敗が出ても、その日は在庫から出るので、毎日1本の公開は途切れない。
  | | 在庫の目標（チャンネルごと） | 2本作る日 |
  |---|---|---|
  | 審査前 | 9本（週1回の予約で7本使い、2本残す） | 在庫が8本以下の日 |
  | 審査後 | 2本 | 在庫が1本以下の日 |
- 審査前の9本は、段階Bで先に作りためる（各チャンネル1日2本で約5日）。公開を始めるのは、9本そろってから。
- **在庫は作った順ではなく、型の優先順で出す。** 判定会で軸の型が決まったら、次の予約から軸の型の在庫を先に出し、ほかの型の在庫は後ろに回す（捨てずに探索枠として出す）。在庫が多い審査前でも、当たりの型が公開に反映されるまでの遅れを1週間以内にするため。

### 毎日（数字の見張り。12:07 JST）
- **公開72時間後**（クリック率の数字が落ち着くのを待つ）
  - 表示回数（インプレッション）が1,000回以上あり、クリック率が4%未満なら、サムネをB案に、タイトルを2番目の案に差し替える。
  - 表示が1,000回未満なら、7日後にもう一度見る。
- **公開7日後**
  - 1回目の差し替えの後もクリック率が4%未満なら、2回目の差し替えをする。タイトルは3番目の案、サムネは新しく作るC案。差し替えは1本につき2回まで。
  - 平均視聴率・離脱した位置・登録者・LINE登録数を記録する。
  - 離脱の位置は、下の「直しの規則」に当てはめる。
- **型の後回し**：同じ型の直近5本の平均視聴率が30%を下回ったら、その型のネタを自動で後ろに回す。
- クリック率が API で取れない場合の代わりは §12 に書く。

### 離脱の位置から台本を直す規則（手順書に反映する）
| 視聴維持率のグラフ | 直す所 |
|---|---|
| 最初の30秒で30%以上が離脱 | つかみの型を変える（ネタ帳の次の3本で別の型のつかみを試す） |

### 立ち上げの探索期（最初の3〜4週間）
- チャンネルごとに、競合調査で絞った型を交互に出す。各型5本以上。
- 型D（AI検証）は、最初の10本のうち4〜5本にする（型D を続けて出すのは2本まで。仕事は1本目を A-4、2本目を型D にする）。全部を型D に寄せない。型D の割合は、8週の判定会で型ごとの数字を比べて決める（付録A）。細かい並びは各チャンネルの手順書 §3・§8。型D の2本目の公開から14日目の週報で、早い見直しをする（付録A の「早い見直し」の行。型D とほかの型がそれぞれ2本以上公開されている時だけ判定し、届かない時は次の週報に持ち越す。Claude が週報で当てはめ、結果を1行で知らせる。本人が決めることは増やさない）。
- 判定に使うのは、表示が1,000回以上ある動画だけ。並べる指標は「クリック率 × 平均視聴率 × 1万回あたりの登録」。
- ただし、1,000回の再生あたりの LINE 登録が、そのチャンネルの平均の半分に届かない型は、軸にしない。1位と2位の指標の差が2割以内なら、LINE 登録の多い方を軸にする（収益の半分は LINE から来るため）。週報には、型ごとの1,000回あたりの LINE 登録も並べる。
- 立ち上げ直後は再生が少ない（§7 の中央の置き方で1本数百回）。再生の数ではなく、クリック率と視聴率の高さで勝ち負けを決める（付録A の4週の線）。この線を使うのは、表示1,000回以上の動画が3本以上ある型だけ。足りない型は、下の「2週間延ばす」に回す。
- 判定は少ない本数で行うので、ぶれる前提で決める。1位を「軸」にし、2位は探索枠に残す。
- **表示が1,000回に届かない型の扱い**
  - 本数は足さない。先にサムネとタイトルを、ほかの型で勝った文言と構図に替える。
  - 4週目の時点で、表示1,000回以上の動画が3本未満の型があれば、その型だけ探索を2週間延ばす。延ばしても届かなければ、その型を外して別の候補と入れ替える。
- 軸が決まった後は、軸の型を7割、探索の型を3割にする。スキルの 02「軸は残し、新しい主役は半分まで」に合わせている。
- 月1回、視聴者の年齢と性別を見て、主役をその層に寄せる。実例ではこれが最も効いた。

  1. 「今週あなたがやること（最大3行）」
  2. 判定会の結論を1行で：**続ける／変える／止める** のどれか（増やせる時は「続ける（増やす）」と書く）。線の細かい数字は付録Aにある
  3. 仕組みの健康状態を1行で：毎日の実行と見張りの最後の実行時刻、在庫の本数、来週分の予約が入っているか、GitHub の使用額（上限の何%か）、道2なら Google ドライブの使用量
- 細かい数字はその下に置く。LINE のブロック率（§5A）と、広告が付きにくい回（§6の8）もここに出す。

## 3. どこで動くか（Claude 用。読まなくてよい）
| 部分 | 置き場所 | 理由 |
|---|---|---|
| 毎日の実行 | GitHub Actions（非公開リポジトリ `yt-auto`） | PCを閉じていても動く。ffmpeg を入れられる。鍵を Secrets に預けられる |
| 台本・調べもの・週報 | Claude Code を Actions の中で動かす（`claude -p`、本人の Max プランのトークン） | 追加のお金がかからない。最上位モデルで書ける。枠が尽きた時の切り替えは §4 |
| 事実確認・絵の照合・続きを見たくなるかの判定 | Gemini | 書いたAIと別の会社のAIに見せて、同じ思い込みでの見逃しを減らす |
| 声 | Gemini TTS（3.8 Flash TTS） | 自然で、1本約26円。語り手の声と話し方はチャンネルごとに固定し、章ごとに調子を変える |
| 絵 | 第一候補は Lovart の公式 API（`agent_skill.py`。鍵は `LOVART_ACCESS_KEY`・`LOVART_SECRET_KEY`）の無料モードで Nano Banana 2（控えは Nano Banana Pro）。クレジットの確認（pending_confirmation）が出たら押さずに控えへ回す。控えは画像API（OpenAI gpt-image-2・Google Nano Banana 2）で、Lovart が当日 01:30 までに終わらない時と、無料の期間が切れた後に使う | 絵の代金が0円になる（本人が払っている Lovart の月額の中）。参照画像で主役の見た目をそろえられる。スレッドを分ければ並べて頼める（1スレッド1件まで） |
| 動くカット | グラフ・表・年表・地図・数字のカウントアップを、プログラムでアニメにする（無料） | 静止画だけの動画にしない。中身は自前で集計したデータ（§6） |
| 組み立て・サムネ | スキルの `build_long.py` と `make_thumb.py` を写し、少し直したもの | 動いている物を使う。直す所は §5⑧ |
| アップと数字の取得 | スキルの `youtube_upload.py` を写して直したもの。権限は「YouTube の管理（youtube と youtube.force-ssl）」と「アナリティクスの読み取り（yt-analytics.readonly）」。収益化の後に「収益の読み取り（yt-analytics-monetary.readonly）」を足す | アップ・サムネ・タイトルの差し替え・コメントの投稿と、クリック率・視聴率・広告が付いた再生の取得に必要（元のスクリプトの権限では足りない） |
| 審査前の受け渡し（道2のとき） | Google ドライブの専用フォルダ。権限は「このアプリが作ったファイルだけ（drive.file）」 | API が自動で上げた動画を公開に切り替えられない場合に、本人が Studio から上げる元にする（§5⑪） |
| LINE の登録経路・特典・ステップ配信 | UTAGE（単独用）。流入経路を動画ごとに1本作る。特典の置き場とステップ配信も UTAGE | どの動画から何人登録し、どの案内で何人押したかが分かる（§5A） |
| 途中の作り物（声・絵） | GitHub Actions の一時保管（キャッシュ。1リポジトリ10GBまで）。段ごとに、その段で増えた物だけを、成功でも失敗でも保存する（`actions/cache/save` を `if: always()` で）。キーは「チャンネル-日付-段-実行番号」、読み出しは「チャンネル-日付-段-」の前方一致。その回が上がったら、翌日にその回のキャッシュを消す（`gh cache delete`） | 失敗してやり直す時に、作った絵と声を使い回す（お金を二重に払わない）。キャッシュは同じキーに上書きできないので、実行番号でキーを分ける。段ごとに作業フォルダ全体を保存すると同じ物が重なり、数日で10GBを超えて今の回の分まで消えるので、増えた物だけにする |
| GitHub の外の見張り | Healthchecks.io（無料の死活監視）。合図の受け口を3つ作る（毎日の実行 job・毎日の実行 spi・見張り）。それぞれ成功したら合図を送り、32時間（間隔1日＋待ち8時間）合図がなければ本人にメールが届く。片方のチャンネルだけ止まっても分かる。02:07 の失敗では合図を送らず、08:07 のやり直しも失敗した時だけ失敗の合図（`/fail`）を送る（やり直しで成功した日は合図の間が約30時間になるので、26時間だと誤報になる）。`PAUSED` で止めている間も、成功の合図は送る | GitHub の使用上限に当たると、見張りも含めて全部止まる。そのときも気づけるようにする |
| 段の進み具合（status.json） | `history/` に commit する（小さいファイル） | 失敗した回でも消えない。やり直しはここを見て続きから始める |
| 完成した動画 | YouTube に非公開で上げる（道1）か、Google ドライブに置く（道2）。どちらも在庫 | 動画は1本で数百MBあるので、GitHub に置かない |
| 記録 | リポジトリの `history/` に、小さいファイルだけ毎日保存（台本・出典・ゲートの結果・お金・最後の実行時刻） | 似すぎの判定と週報、見張り役どうしの見張りに使う |
| 停止スイッチ | リポジトリの設定値 `PAUSED` を `true` にする | スマホのブラウザ（PC 版サイトの表示）から止められる。スマホの GitHub アプリでできるかは公式では未確認（手順は §9） |
| 段階Aの鍵の置き場 | PC の `C:\yt-auto-secrets\`（OneDrive の外）。鍵は `keys.env`、YouTube のログイン情報は `client_secret.json` と `token_<ch>.json`。プログラムは `C:\yt-auto\` | 段階Aは PC で1本を通すので、鍵を PC に置く。Claude はこのフォルダを開かない（中身を表示しないプログラムで、値があるかだけを確かめる）。後半の準備で、このファイルから `gh secret set -f` で GitHub に一度に入れる（準備手順書 B5）。段階Aでも §4 の「作業を2つに分ける」を守り、調べものをする Claude を、keys.env を読み込んだ環境で動かさない（書く作業には鍵を渡さない） |

## 4. リポジトリの中身と、確実に回すための決まり（Claude 用。読まなくてよい）
```
yt-auto/
  .github/workflows/
    daily.yml     … 毎日 02:07 JST に、job と spi を並べて同時に作る（チャンネルごとに別の作業。上限は各4時間）。08:07 JST にもう1回起動し、失敗した回だけ続きからやり直す
    watch.yml     … 毎日 12:07 JST に、数字の見張り（§2）と、在庫・最終公開・毎日の実行の見張り
    weekly.yml    … 日曜 21:07 JST に、週報・ネタ補充・改善案・UTAGE の流入経路づくり・LINE の声の取り込み。毎月第1日曜は特典の更新も
  vendor/youtube-video-maker/   … スキルの scripts と templates の写し（スキル本体は書き換えない）
  pipeline/       … run_daily.py（司令塔。段ごとに status.json を書き、失敗した段から再開する）ほか
  channels/job/ と channels/spi/
    profile.json   … 語り手（名前・口調・立場）、声と話し方、画風、BGM、公開時刻、概要欄の定型文
    編集方針.md     … このチャンネルが何を独自に届けるか（§6）。審査で説明する材料
    手順書.md       … 型のルールと、型ごとの章の組み方（ルールは1か所だけ）
    line_scenario.md … LINE のステップ配信の文面（§5A）
    ネタ帳.json / 禁止表現.txt / style_ref/
  data/           … 自前データの元（公的統計・暦など）と、その出どころ
  data/voices/    … LINE 登録者のアンケート集計と、掲載の許可を得た体験談（名前・連絡先は入れない。保存は12か月まで）
  assets/bgm/     … 使ってよいBGMだけ（出どころを bgm_sources.md に記録）
  history/<ch>/<日付_題>/
  requirements.txt … 使う部品の版を固定する
  .gitignore      … .env・鍵・ログイン情報・作業フォルダ・動画を、リポジトリに入れない
```

### 確実に回すための決まり
- **日付は全部、日本時間で扱う。** GitHub Actions の予定は UTC で書くので、02:07 JST は UTC では前日の17:07 になる。プログラムは全部 `TZ=Asia/Tokyo` で動かし、日付はタイムゾーン付きで持つ。「明後日」「公開日の3〜10日前」「吉日」の判定は、日本時間の日付で行う。
- **固定データは照合してから使う。** 暦の計算ファイル・手取りの料率・e-Stat 以外の統計など、前もって `data/` に置いたファイルは、中身のハッシュを `data/checksums.json` に記録して一緒に commit する。毎日の実行の最初に全部照合する。
  - 一致しない時：その日の新しい制作を止めて Issue を立てる。公開は在庫で続ける。Claude が差分を見て、正しい方に戻すか、作り直してハッシュを更新する。
  - 有効期間のあるファイル（暦は2027年12月まで、料率は年度ごと）は、公開日が期間の外なら、その題を使わず次の題に回し、週報に出す。
- **作業を2つに分ける。**
  - ①書く作業：Claude が担当する。持たせる鍵は Claude のトークンだけ。
  - ②作る・上げる作業：声・絵・組み立て・アップ・UTAGE。こちらで他の鍵を使う。
  - ①はネットで調べ物をする。読んだページに悪い指示が混ざっていても、鍵を盗まれないようにするために分ける。
- **同時実行の枠を分ける。**
  - 1つの枠にまとめると、待っている2本目以降が黙って取り消される。だから枠を分ける。
  - 毎日の実行はチャンネルごとの枠（`daily-job`・`daily-spi`）。見張りは `watch`、週報は `weekly`。全部 `cancel-in-progress: false`。
  - 記録の保存がぶつかったら、最新を取り込んでから5回までやり直す。
- **最後に必ず通知の段を動かす。** 成功でも失敗でも、最後に通知の段を動かす（if: always()）。失敗したら Issue を立てる。同じ原因の Issue がすでにあれば、そこに1行足すだけにする。
- **見張り役どうしで見張る。**
  - 毎日の実行・見張り・週報は、それぞれ最後の実行時刻を `history/heartbeat.json` に書く。
  - 見張りは「毎日の実行が26時間ない」、毎日の実行は「見張りが48時間ない」、どちらも「週報が8日ない」を見つけたら Issue を立てる。
  - 週報の冒頭にも、3つの最後の実行時刻を出す（§2）。
  - GitHub ごと止まった時（使用上限・障害）に備えて、外の見張り（Healthchecks.io）にも毎日合図を送る（§3）。
  - 予定の起動は、GitHub が混んでいると数分〜数十分遅れることがある。各段の時刻には余裕を取ってある。
- **版を固定する。** 次のものは版を固定する。
  - 実行環境（Ubuntu 24.04）
  - Claude Code の版
  - Python の部品（requirements.txt）
  - 日本語フォント（fonts-noto-cjk）
  - フォントの名前が字幕の設定と合っているかは、組み立ての前にプログラムで確かめる。
  - 版を上げるのは月1回。上げたら1本通して試してからにする。
- **外のサービスに速く頼みすぎない。**
  - 画像・声は同時に4本まで頼む（2チャンネル同時に動くので、チャンネルごとに2本）。混んでいると言われたら、待つ時間を倍にしながら5回までやり直す。
  - バッチで頼んだ絵が当日の 01:30 までに届かなければ、残りは普通の頼み方で作る。
- **お金の上限は、見積もりより厳しめに判定する。**
  - 毎回、見積もり額に「補正係数」を掛けて累計する。補正係数は、段階Aの1本目の「実額÷見積もり」。上限の判定は段階Bから始めるので、そのときには実額の係数が入っている。月1回の請求確認で直す。
  - 1本目の実額が取れなかった時だけ、仮に1.5を使う。
  - 累計が `MONTHLY_CAP_YEN` に届いたら、その月は新しく作るのを止め、在庫で公開をつなぐ。
  - OpenAI は使用量を API で取れるなら、毎日の実額で判定する（§12）。
- **Claude の枠が尽きたときは、API キーに切り替える。**
  - Max プランの枠には、5時間ごとの枠と週ごとの上限がある。尽きた日は、08:07 のやり直しで次の枠を使う。
  - それでも書けなければ、Claude の API キーでの実行に自動で切り替える。1日の上限を300円にする。
  - この切り替えは、本人がお金の了承をした後にだけ有効にする。了承がなければ、その日は在庫で公開をつなぐ。

## 5. 各段の中身（Claude 用。読まなくてよい）

### ① ネタ
- `ネタ帳.json` から、§2 の比率で1つ選ぶ。比率は、探索期は型を交互、その後は軸7・探索3。
- ネタ帳の1行には、題・型（type）・骨組み（frame）・向ける人（target）・公開できる期間（window_start・window_end。期間のない題は空）・自前データの元（data_ref：統計の表IDと職種コード、または暦の計算ファイル）を持たせる。
- 選ぶ順：①公開予定日が期間に入っている題（期間の終わりが近い順）②期間のない題。期間が過ぎた題は、翌年へ回す。
- 補充の時に、data_ref から実際に値が取れるかをプログラムで確かめる。取れない題はネタ帳に入れない。
- 型の切り替え（例：スピの型C を2月から別の型にする）は、日付つきの設定（`profile.json` の types）で持ち、判定会の集計は型ごとに分ける。
- 週1回、Claude が20本を補充する。材料は、競合の伸びた動画、自分の数字、LINE 登録者のアンケートと質問（§5A）。
- 競合から借りるのは「題材の傾向と構成」だけ。台本の文・絵・サムネ・図は写さない。

### ② 調べもの・自前データ
- Claude にネットで調べさせ、使う事実を `facts.json` に残す。書く項目は「事実・数字・出典URL・確かさ」。台本に入れてよい数字・年・決まりは、出典があるものだけ。
- 毎回、自前データを1つ入れる（§6）。次のどちらかをプログラムで集計し、グラフや表にする。
  - 公的な統計や暦。元データは `data/` に置き、出どころを記録する。
  - LINE 登録者のアンケートの集計（回答30件以上の問いだけ）。「このチャンネルの LINE 登録者に聞きました（回答○人）」と、回答した人数を必ず画面と台本の両方に出す。
- `claude -p` には、使ってよい道具だけを指定して渡す（調べる・読む・ファイルに書く）。

### ③ 台本
- スキルの `script_long.json` の形で書く。
  - 決まった語り手が案内する（§6）。
  - 長さ：3,000〜3,800字・100カット前後。8分以上あれば、途中に広告を入れられる。
  - 型D（AI検証）は20〜25分・7,000〜8,500字（推測）・14〜18章。章の数は骨組みで決まる（仕事は初めての回で14〜16章、コメントからの章が入る回で15〜17章。スピは「次の重なり」の章があるので15〜17章と16〜18章。各チャンネルの手順書 §3）。長いほど途中の広告が増え、総再生時間にも早く届く。スキルの `check_script.py` の字数の決まりは、段階Aで型D に合わせて直す（それまでは、型D の字数を手順書 §3 の範囲で判定する）。
- **章の組み方は、型ごとに変える。**
  - 全部の回で共通にするのは、つかみ2つ・前置き3文以内・呼びかけの位置・表示だけ。
  - 章の並べ方（骨組み）は、`手順書.md` に型ごとに別々に書く。例：
    - 順位型：下位から上位へ数えていき、1位の前にクイズ
    - 比較型：2つを5項目で並べ、項目ごとに判定
    - 追いかけ型：1人の1年や1日を、時間の順に追う
    - 暦型：月の行事を日付の順に
    - 由来型：1つの作法の始まりを、時代の順に
    - 採点型（型D）：よく聞く説を5〜6つ「容疑者」として立て、1つずつ統計・暦・記録と照らす。説2と説4の章の頭でクイズ、決め手の章の後に「ここまでのおさらい」の章（説の名前を出てきた順に言い直すだけで、順位と点数は言わない）を置き、最後に「AIの採点結果」の棒グラフで初めて順位と点数を出す。点数は、段階Aで固定する機械的なランク表（`data/scoring_rank.json`。資料の種類ごとの点と、反対の資料が1つあるごとの一律の減点）からプログラムが計算する。Claude は各説に支える資料と反対の資料を割り当てるだけで、点を足し引きしない
  - 1つの型の中でも組み方を3通り持つ。山場の位置（前半・中盤・終盤）とクイズの有無を変え、続けて同じ組み方は使わない。軸7割の時期でも、骨組みが毎回同じにならないようにするため。
  - 山場の材料は、毎回違う物を使う。自前データ・調べた事実・LINE 登録者の体験談（掲載の許可を得たもの）から1つ。
  - 体験談は、文をそのまま読み上げない。語り手が要点を紹介し、名前・会社名・地名など本人が分かる情報は出さない。
- 呼びかけの位置と特典
  - LINE の案内は、全体の40〜45%あたりで1回。型D（20〜25分）だけ、95%あたり（±3%。結論の後、締めの前）に別の文でもう1回入れる（長い回で、最後まで見た人にも届けるため。各チャンネルの手順書 §4 と同じ）。
  - チャンネル登録の呼びかけは、65%あたりで1回。2つを離す。
  - LINE の特典は、その回の中身の続きにする（特典の作り方は §5A）。
  - 特典は、その回の数字や暦をまとめた配布物にする。
- 語り手の話し方
  - 仕事：数字から言えることは言い切る。タイトル・つかみ・呼びかけでは「〇〇は辞めとけ？ 統計で答え合わせ」「辞める前に見て」のような言い切りを使ってよい。根拠はその回の統計の数字にする。
  - スピ：「最強開運日」「金運」「やってはいけないこと」など、競合と同じ強さの言葉を使う。言い伝えは「昔から〜と言われてきた」と流れの中で語る。書かないのは、具体的な結果の保証（必ず当たる・〇万円入る）と、病気・健康への効果だけ。
- 章ごとに話し方を指示して、声が単調にならないようにする。

### ④ 台本ゲート（全部に合格したら進む。不合格なら書き直す。書き直しは2回まで）
| 見ること | やり方 | 合格の線 |
|---|---|---|
| 形 | スキルの `check_script.py --long` | 注意が0件 |
| 事実 | Gemini が出典と照らし合わせ、検索でも裏を取る | 出典と食い違う所が0件。出典なしの断定が0件 |
| 似すぎ | 過去の全台本と、文字の重なり（3文字単位）・つかみの言い回しを比べる | 一致率が35%未満。同じつかみが0件 |
| 文体の偏り | 直近14本と比べる（文末の言い方の割合、つかみの型の偏り） | 1つの文末が全体の4割未満。同じ型のつかみが3回続かない |
| 骨組みの偏り | 直近の同じ型の回と、章の組み方を比べる | 同じ組み方が2回続かない |
| 禁止表現 | `禁止表現.txt` と、Gemini の判定 | 各チャンネルの手順書 §4 の「書かないこと」・特定の人や会社をけなす書き方・体験談の本人が分かる情報が0件。§6 の8で消した守りの断り書きが戻っていない |
| 広告に向くか | Gemini が、YouTube の「広告掲載に適したコンテンツのガイドライン」の項目（強い言葉・暴力・性的な話・薬物・人を傷つける話題・あおるタイトル）で台本・タイトル・サムネの文字を見る | 当てはまる所が0件。収益化の前は Studio の黄色いアイコンが出ないので、ここで先に見ておく |
| 続きを見たくなるか | Gemini が、最初の30秒・各章の終わり・山場を10点満点で採点する | 最初の30秒が7点以上。どの章も5点以上 |

### ⑤ 声
- Gemini TTS でカットごとに作る。止まったら、待つ時間を倍にしながら5回までやり直す。
- 読み間違えやすい語は、台本の段で `tts_text` に読みを入れておく。

### ⑥ 絵と動くカット
- 1本につき、絵70枚（作り直しを含めて約75回作る）と、動くカット15〜20。画面の切り替わりは合わせて85〜90。
  - スキルの実例の「80〜90枚相当」を保つ。実例では、使い回しの多い回ほど登録が減った。
  - 型D（20〜25分）は、AIの絵を70枚までにし（場面の絵だけ）、画面の切り替わりを長さに合わせて約190〜240に増やす（推測）。増えた分は、プログラムで作る図・グラフ・出典カード・採点結果の棒グラフで埋める（代金がかからない）。スピは著作権の切れた浮世絵・錦絵も使い、作品名と出どころを `assets/ukiyoe_sources.md` に残す。
- サムネ用の背景を2枚作る（2回目の差し替え用のC案は、そのとき作る）。
- 翌日分の絵は、前日の「書く作業」が終わった時点でまとめて頼む（§4）。
- 主役の見た目は、`style_ref/` の参照画像でそろえる。
- 実在の人物・企業のロゴ・他人の画像や図は使わない。図は全部自前で作る。

### ⑦ 絵ゲート
- スキルの `check_sheet.py` で一覧を作り、Gemini が1枚ずつ見る。見ること：
  - セリフと合っているか
  - 出てこないはずの人がいないか
  - 時代と時間帯
  - 崩れ
  - 読める文字やロゴ
  - 実在の人物や有名キャラに似ていないか
- 不合格の絵は作り直す（1枚につき2回まで）。それでも直らなければ、近い絵を使い回す。使い回しが15%を超えたら、その回は止めて在庫で公開をつなぐ。

### ⑧ 組み立て
- スキルの `build_long.py` を土台に、3か所を直す。
  - **処理を軽くする**：絵を動かすときの拡大を、2倍から1.5倍にする。仕上げの圧縮は速い設定にする。
  - **声の大きさをそろえる段を足す**：約 −14〜−16 LUFS（LUFS は音の大きさの単位）。
  - **字幕のタイミング**：カットごとの声の長さを、文字数で割って決める。音声認識の Whisper は使わない。
  - **「再現イメージ」と「イメージ」の部品を足す**：スピの昔の場面のカットの間は「再現イメージ」、仕事の型B の A社の場面のカットの間は「イメージ」と、画面の右上の隅に小さく出す専用の部品にする（強調用の label とは別。読み上げない。A社は統計から作った会社で、実際の出来事の再現ではないため、仕事は「再現」と書かない）。仕事の型B・C の「平均的な〇〇さん」の名札も、同じ部品で紹介のカットに1回出す。
  - **書き出しの大きさ**：ビットレートの上限つきで書き出す（目標約4Mbps。10分で約300MB）。元の設定（crf17）のままだと1本1GB近くになり、道2のドライブに入りきらないため。型D は図とカードが多く動きが少ないので、目標を約2.5Mbps にする（25分で約470MB）。
- 最初の1本で処理時間を測り、1本60分以内に収める。型D は90〜120分を見込む（推測。最初の型D の1本で測る）。1日の上限は各チャンネル4時間なので、2本作る日のうち型D は1本までにする。

### ⑨ 完成品ゲート
- 長さが8分以上（型D は20〜25分）。音の大きさが目標から±2以内。3秒以上の無音がない。
- 10か所の静止画を切り出し、文字のはみ出しや重なりを Gemini が確かめる。

### ⑩ サムネとタイトル
- タイトルを3案、サムネを2案作る。1案目には、手順書の「勝ちパターン」を使う（§2）。
- スマホの大きさで読めるかを、Gemini が確かめる。
- 型D は、タイトルに「AIに〈資料の名前〉だけで」を入れ、「AI」を前の32字に置く。サムネの文字には「AI」を入れない（色と点検は各チャンネルの手順書）。

### ⑪ アップ
- 説明文の並び（チャンネル看板 v11 の説明文と同じ流れ）
  1. LINE の案内（その動画の型の特典の名前と「LINEで無料で受け取れます」＋その動画専用の UTAGE の流入経路のリンク）。PR は付けない（無料の特典の受け取り口で、広告ではないため。PR は LINE の中のアフィのリンクにだけ付ける。§6 の8）
  2. 出典。e-Stat の API で取った統計を使った回（どちらのチャンネルでも）は、e-Stat の決まりの1文「このサービスは、政府統計総合窓口(e-Stat)のAPI機能を使用していますが、サービスの内容は国によって保証されたものではありません。」と、「〇〇（調査名・府省）を加工して作成」を書く。LINE の特典の表の下にも同じ2つを書く。点検でこの2つがあるかを見る
  3. AI の行（各チャンネルの手順書の文。「人の手では数えきれない〜を計算し、AIで映像と声にしています」と、AIだからできることとして書く。スピの型D で暦のほかに統計も使う回は、照らした先の文を「日付は暦と、数字は統計と照らしています。」にする）
  4. チャプター
- 「AIで作った映像・声」の申告（containsSyntheticMedia）をオンにする。道2では本人が Studio で同じ申告をする。週報の前に、公開済みの全動画の申告がオンかを API で確かめ、オフの回があれば「今週やること」に挙げる。
- 公開後、チャンネルからのコメントを1件入れる（LINE の案内と同じ文とリンク。PR は付けない）。固定は API でできないので、審査前は本人が予約のときに固定する（1本10秒）。審査後は固定しない。
  - 見張りの段で、入れたコメントが残っているかを確かめる。リンクつきのコメントが YouTube に消された回が2本出たら、そのチャンネルはコメントをやめ、概要欄の1行目だけにする。
- 終了画面とカードは API で付けられないので使わない。
- 同じ動画を2回上げないために、上げる前に2つ確かめる。どちらかがあれば上げない。
  - `history/` の uploaded.json
  - チャンネル内に、同じタイトルの動画がないか
- **審査が通るまでの公開のしかた（2通り。段階Aの1本目で、どちらになるかを確かめる）**
  - 審査前の API で上げた動画が「非公開」に固定されるかは、公式の文書どうしが食い違っている（2020年の告知は「固定する」、2026年10月の videos.insert の説明は「固定しない」）。段階Aの1本目を「限定公開」で上げて確かめる。固定されなければ、審査は申し込まずに道1で進める。固定された時だけ審査を申し込み、本人が Studio で公開に切り替えられるかも確かめる（§12）。
  - 道1（切り替えられる場合）：非公開で上げて在庫に入れる。本人が週1回、Studio で、翌週の14本（2チャンネル×7本）の公開日時を予約する。1本約2分。
  - 道2（切り替えられない場合）：YouTube には上げず、1本ずつのフォルダにして Google ドライブに置く。本人が週1回、Studio から14本を予約アップロードする。1本約3分。
    - フォルダの中身：動画（1本300MB以下に圧縮。型D は約470MB。14本の半分が型D で約5.4GB、無料の15GBに収まる）、サムネ2案、タイトル、説明文、タグ、公開日時、`確認表.txt`。
    - `確認表.txt` は2行だけ：①「AIで作った映像・声」の申告にチェックしたか ②説明文を貼ったか（貼れば LINE のリンクと出典がそろう）。本人が手で見るのは①だけ。
    - **本人が上げた動画を、仕組みが見つける。** 見張り（watch.yml）が毎日、チャンネルのアップロード一覧を API で読み、ドライブに置いたタイトルと照らし合わせる。見つかった動画の ID を `history/` の uploaded.json に書く。タイトルが合わない時（本人が直した時）は、予約日時と長さで照らす。それでも見つからない回は週報に挙げる。
    - ID が登録された後は、コメント・数字の見張り・サムネとタイトルの差し替えが道1と同じに動く。差し替えが API でできない場合だけ、週報に差し替え案を出し、本人が Studio で替える（1本約1分）。
    - ID が登録された動画は、ドライブから消す。週報の健康状態の行に、ドライブの使用量を出す（12GBを超えたら Issue）。
- **予約忘れの検知（審査前）**：見張りが毎日、「明後日に公開予定の動画があるか」をチャンネルごとに確かめる。無い場合は、日曜の週報の「今週やること」の1行目に出す。月曜の見張り（12:07）でもまだ無ければ Issue を立てる。それでも空いた日は、在庫があっても公開が抜ける（審査前は仕組みが自分で予約できないため）。
- 審査が通った後：在庫から毎日1本、翌日19:00などの公開予約を自動で入れる。

### ⑫ 記録
- `history/` に保存し、`記録.md` に1行ずつ書く。書く項目は次のとおり。
  - 日付、題・型・章の組み方、ゲートの結果、処理時間
  - かかったお金：見積もり×補正係数の累計（§4）。実際の請求額は月1回、本人が各社の画面で確かめる。
  - 人の編集：本人が直した所の前後の差分（§6の7）

## 5A. LINE の流れと特典（本人が読む）
YouTube から LINE に来た人に、登録した日から自動で届く流れ。アフィの収入はここから生まれる。

### 全体の流れ
```
動画の40〜45%あたりの案内（型D は95%あたりにもう1回）→ 概要欄の1行目とコメントの動画専用リンク（UTAGE の流入経路）→ LINE 登録
  → 0日目：特典が届く ＋ 1問アンケート
  → 1日目以降：ステップ配信（下の表）→ アフィの案内（月2回まで）
  → 回答とクリックは UTAGE に記録 → 週報で、どの動画・どの案内が効いたかを見る
```

### ステップ配信（チャンネルごとに `line_scenario.md` に文面を書く）
| 日 | 仕事と職場 | スピ開運 |
|---|---|---|
| 0日目 | 特典（その動画の型の特典。手順書 §4 の表。例：主な職業の年収・労働時間と、産業別の離職率の一覧）。語り手のあいさつ。1問アンケート「今いちばん近いのは？ 辞めたい／転職を迷っている／人間関係／お給料」 | 特典（その動画の型の特典。手順書 §4 の表。例：今月と来月の吉日と行事のカレンダー）。語り手のあいさつ。1問アンケート「気になるのは？ お金／ご縁／厄よけ／季節の行事」 |
| 1日目 | 回答に合わせた過去動画を1本 | 回答に合わせた過去動画を1本 |
| 3日目 | 回答別の案内（アフィのリンクに PR）。「辞めたい」→ 弁護士・労働組合が運営する退職代行の「違いの一覧」（運営元・料金・できること）と、まず相談するならこの1つ。「転職」→ 大手の紹介会社の「違いの一覧」と、まず登録するならこの1つ | 回答に合わせた行事の過ごし方。PR は付けない |
| 7日目 | 「あなたの体験を聞かせてください」（動画で紹介してよいかを選んでもらう）＋新着動画 | 同じ |
| 14日目 | 回答別の案内（アフィのリンクに PR。3日目と別の切り口） | 占いの案内（アフィのリンクに PR） |
| 以降 | 週1回の新着動画のお知らせ。アフィの案内は月2回まで | 同じ |

- 文面は Claude が書く。守るのは、アフィのリンクの PR と、各 ASP・案件が決めている禁止の言い方だけ（守らないと報酬が取り消される）。急ぎを伝える言い方や強い引きは使ってよい。本人が確認してから UTAGE に入れる。配信を始めるのは、本人の OK の後。
- **ブロック率で案内の早さを直す。** 週報に、配信の日ごとのブロック率を出す。3日目の配信の後のブロック率が20%を超えた週が2回続いたら、最初の PR を7日目に、2回目を21日目にずらす。

### 体験談の扱い
- 7日目に集まった体験談とアンケートの回答は、weekly.yml が UTAGE から取り込み、`data/voices/` に置く。名前・連絡先は取り込まない。文中に名前・会社名・地名が混ざっていないかも取り込む時に Gemini が確かめ、混ざっていたら伏せ字にしてから置く。
- 動画で使うのは「紹介してよい」を選んだ人の分だけ。選んだ記録（日時と選んだ答え）は UTAGE の回答としてそのまま残し、`data/voices/` にも回答の番号を書いておく。
- 「やっぱり使わないで」と連絡が来たら、次の動画から使わず、`data/voices/` からも消す。公開済みの動画は、本人が分かる情報を出していないので、そのままにする（取り下げを強く望まれた時は本人と相談）。0日目の配信に、この連絡の仕方を1行書いておく。
- 保存は12か月まで。過ぎた分は weekly.yml が自動で消す。

### 特典の作り方（自動）
- 仕事：`data/` の公的統計から、型ごとの一覧表（手順書 §4）を1枚の画像と PDF にする。毎月第1日曜に weekly.yml が作り直す。
- スピ：暦の固定ファイル（手順書 §8）から、型ごとのカレンダーと早見表を画像と PDF にする。月ごとのカレンダーは、毎月第1日曜に「今月と来月の2か月分」を作る（来月初めの吉日を紹介する回でも、特典に載っているようにするため）。型D の特典は、吉日カレンダーに「言い伝え早見表（丙午・六曜・厄年など）」を添えた2つセットにする（同じ仕組みで作る。最初の版は段階Aで作る。スピの手順書 §3・§4）。
- 特典ファイルには有効月を持たせる。毎日の公開の前に、その動画の型の特典が、その回で紹介する日付の月（日付のない回は公開月）を含むかを確かめる。古ければ、その場で作り直しを動かす。それも失敗したら Issue を立てる（公開は止めない）。同じ特典の Issue は1つにまとめ、翌日からはそこに1行足すだけにする（§4 の通知の決まり）。
- UTAGE に API でファイルを上げられない場合（§12）：weekly.yml が新しい特典を作って Google ドライブに置き、週報の「今週やること」に「UTAGE の特典を差し替える（約5分）」を出す。本人の作業は月1回。差し替えたら、本人が週報のコメントに「差し替えた」と返し、仕組みがその日付と特典の版を `data/tokuten_utage.json` に書く。この場合の有効月の確認は、repo のファイルではなく `data/tokuten_utage.json` の版で行う（UTAGE に古い特典が残ったまま合格にしないため）。
- できた特典は UTAGE に上げ、0日目の配信に付ける。特典は動画ごとではなく、型ごとに作る（各チャンネル2〜3種類。中身は各チャンネルの手順書）。動画ごとの流入経路に、その動画の型の特典を結びつける。動画の中の案内は、その型の特典の名前で言う。

### アフィの計測
- 案内のリンクは、案件ごと・配信の日ごとに UTAGE のクリック計測を付ける。
- felmat に「どこから来たか」を付ける欄（サブID）があれば、そこにも動画の番号を入れる（使えるかは §12 で確かめる）。
- 週報には、動画ごとの LINE 登録数、案内ごとのクリック数、felmat の成約数を並べる。
- アフィ以外の売り先（有料の鑑定・相談・自分の商品）は、この設計の損益に入れていない。チャンネルごとの LINE 登録者が1,000人を越えた後の判定会で、足すかを本人が決める。足す場合も、案内は月2回の枠の中で分け合う。

### LINE の費用の上がり方（推測。料金は §12 で確かめる）
- 1人に届く通数：最初の月は約8通、その後は月約5通（新着4通＋案内1〜2通）。
- 登録から60日たって、その間に一度もリンクを押していない人には、月1通（新着のまとめ）だけにする。費用を抑え、ブロックも減らすため。これで、2か月目以降の平均は1人月約3通になる見込み。
- プランの目安（各チャンネル）
  - 無料プラン（月200通）：その月の新しい登録者が約25人まで。中央の置き方（§7）では、月2〜3から超える。
  - 月5,000通まで（月約5,000円）：登録者の合計が約1,000人まで。
  - 月3万通まで（月約1.5万円）：登録者の合計が約8,000人まで。それを超えた分は1通約3円の推測。
- 付録B の損益表では、LINE の費用を再生数（＝登録者数）に合わせて増やしてある。
- LINE の月額は、制作費の上限（`MONTHLY_CAP_YEN`）とは別に扱う（§7）。次のプランに上がる見込みの2週間前に、週報で知らせる。

## 6. 量産と見られないための作り
収益化は、人が見て審査し、チャンネル単位で判断される。2026年7月に、型どおりの量産は収益化しないことがはっきりした。このラインでは、次の8つを入れる。目的は2つ。
- チャンネルの個性と独自の中身を見せる。
- 人が関わっていることを、記録で説明できるようにする。

1. **決まった語り手**
   - チャンネルごとに、名前・口調・立場が決まった案内役を1人置く。見た目は、AI で作ったオリジナルのキャラクター。
   - 架空の経歴（元人事、霊能者 など）は名乗らない。案内役は「調べたことを案内する係」として話す。
2. **自前のデータ**
   - 毎回1つ、公的な統計や暦をプログラムで集計した独自のグラフ・表を入れる。
